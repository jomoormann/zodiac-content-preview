  PROTOTYPE NOTES · FOR REFINEMENT
  
      
    
    • Color language: blue = policies and allowed execution · light-blue dashed = governance signatures · sand = risk and attack (the pre-handover direct-rule path stays sand-dashed, wordlessly) · violet = the guardian (council node, veto and exit edges, previewed in ghost state).
      • 
    
    • Cluster boxes contain each policy's members and targets, so internal lines never cross the canvas; the three gate edges leave the boxes and land on the treasury without touching anything.
      • 
    
    • Custom instant tooltips replace native ones; every text is state-aware (budgets, durations, edited settings appear live). Copy inventory lives in tipFor() in the script.
      • 
    
    • Editor modals carry v2 / v3 / delay-mod tags; saving is instant pre-handover and queued after. Every add or signed edit briefly glows the entity that authorized it: owners before the handover, Operator vault after.
      • 
    
    • Attack simulator: five scenarios below the graph, each choreographed on the graph itself (alarms, timelock pings, violet veto flash). Only "Vault admins sign malicious transaction" can drain, and only until the Operator vault (timelock) + Security Council are built; "Member key stolen" leaks one payroll allowance if Payroll is built without the Team wallets whitelist. The hint line says what is missing. Each scenario now runs 3 to 6 beats with its own rhythm (escalating attempts, retries, a realization); per-beat delay is one number in runAttack.
      • 
    
    • Wiring shown: after the handover the Security Council (4/7) is the treasury's 1/1 owner (exit = owner path, veto = owner-signed setTxNonce on the Delay); the Operator vault acts only as a module through the Delay. Verify the v2/v3 mapping of every tagged parameter. Numbers illustrative.
      • 
    
    • Start state: a single key (EOA), no roles; the One key node pulses a slow white glow until it is upgraded, as the cue for the first click; clicking the key or any Zodiac piece upgrades it to the 2/3 multisig first. With one key, key theft and a tricked signature drain everything. Until the Deposits policy exists the DeFi frontend attack drains the vault (or is caught by the operator queue + council veto if those exist), and "Member key stolen" finds nothing to steal. Building Ben, External, Morpho or Lido auto-builds Deposits.
      • 
    
    • The Zodiac wordmark (brand SVG paths, no mark) fades into the top-left of the graph when the first Zodiac component is built and leaves on start over.
      • 
    
    • "Lazarus has infiltrated your organization" replaces the plain owner-key-stolen vector (SEAL: DPRK IT workers section, DPRK playbook): same one-key mechanics, infiltrator narrative, multisig ending points at the complacency vector. All five vectors stay visible; ones that do not apply are greyed with the reason on the tile ("Member key stolen" needs a policy, "Zodiac App hacked" needs a Zodiac component). Tile names follow the setup (owner / quorum / operator admins). The tile that attacks the current default flow carries a "default flow" tag: the malicious-signature vector for a single key and for a plain multisig (complacency: the second signer signs because a signature is already there), "Member key stolen" once roles exist.
      • 
    
    • Third verdict AT RISK (sand): the vault stays full but is "one careless signature away"; used by the Lazarus run whenever a quorum can execute without a council veto behind it (plain multisig, or operator without council). Only the timelock plus council turns it green.
